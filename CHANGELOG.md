## [Unreleased]

### Added

- `brails generate scaffold Post title:string body:text user:references`: the model (registered) and its migration, a JSON controller with the five resource actions and a `StrongParams` field whitelist, a request test on the test database, and `router.resources('posts')` in `config/routes.js`. It checks every target first, so a conflict writes nothing. Generated models now call `register()`. Pinned by `test/cli/scaffold.test.js`, whose PostgreSQL case makes an app with `brails new`, scaffolds into it and runs the app's own test.
- Mail delivery through the configured adapter: `console` (the default, which did not exist) prints each message, and `test` keeps it for `mailDeliveries()` / `clearMailDeliveries()`. `deliver()` builds the message (from the mailer's `defaults.from`, else `mail.from`) and hands it over; `deliverLater()` queues a `DeliverMailJob`. A message with no `to` or no sender throws; `template()` throws until HTML views land; `mail.adapter` set to smtp, sendgrid, postmark or ses fails at boot. A new guide, `docs/eng/mail/overview.md`. Pinned by `test/mail/delivery.test.js`.
- Jobs queue in-process on the memory adapter (the default): `performLater`, `performIn` and `performAt` return the job's id and run it in this process, retried up to `static attempts` times with `static backoff`, with `beforePerform`, `afterPerform`, `onRetry` and `onError` around it (`performNow` runs the callbacks too). `enqueuedJobs()`, `performEnqueuedJobs()` and `clearEnqueuedJobs()` serve tests. `static unique` and `schedule` throw, since only a persistent queue can honor them; BullMQ stays planned. Pinned by `test/jobs/memory_queue.test.js`.
- `brails test` (`t`) runs the app's tests: `bun test` in the app root with `NODE_ENV=test`, every argument after `test` passed through unchanged (`brails test test/models -t "requires a title"`), exiting with its code. It exited 1 as not implemented. Pinned by `test/cli/test_command.test.js`.
- `hasAndBelongsToMany` loads through its join table, through `loadAssociation()`, `includes()` (nested too) and the association reader. The join table defaults to both table names in lexical order (`posts_tags`, with `post_id` and `tag_id`); `joinTable`, `foreignKey` and `associationForeignKey` override it. `loadAssociation()` returned `null` for one, `includes()` skipped it with a warning. Pinned by `test/database/habtm.test.js` and, on PostgreSQL, `test/database/habtm.pg.test.js`.
- `request(app)` sends test requests through an initialized app in-process, through the new `app.handle(request)` (routing, middleware and the action, no server): `await request(app).get('/posts', { page: 2 })`. The exported `request` was a `TestRequest` bound to no app, whose requests resolved `undefined`. Pinned by `test/testing/request.test.js`.
- Test-database helpers. `setupDatabase()` connects to the database `config/database.js` names for `NODE_ENV=test`, loads `db/schema.js` into an empty database and runs pending migrations, dropping nothing. `withinTransaction(cb)` runs a test body in a transaction that always rolls back (it threw `NotImplementedError`, and before that never ran `cb`). `cleanDatabase()` truncates every table but `schema_migrations`, restarting ids, and refuses unless `NODE_ENV` is `test`. Pinned by `test/testing/database.test.js`, and on PostgreSQL by `test/testing/database.pg.test.js`, which CI's framework job now runs against a `postgres:16` service.
- Nested resources and `scope(path, callback)`. A `resources` callback nests its routes under `/posts/:post_id` (the parent param singularized by the inflector, so `categories` gives `:category_id`); before, `scope()` ignored its path and the nested routes landed at `/comments`. `scope` prefixes the path without touching the controller, a segment can be a param (`scope('/:locale', ...)`), and scopes, namespaces and nesting stack in the order written. The router's own one-line `singularize` is gone. Pinned by `test/routing/scope_and_nesting.test.js` and the routing guide's test, which runs the guide's Nesting and scopes code against its table.
- `brails generate` (`g`) `migration`, `model` and `controller`. A `Create<Table>` migration gets a `createTable` with the fields and timestamps; a model gets `belongsTo` for `references` fields plus its create migration; a controller gets an action per name, in a subdirectory when namespaced. Existing files are never overwritten, migrations generated in the same second get distinct versions, and unknown column types are refused. scaffold, job, mailer, channel, component, auth and admin still exit 1 as not implemented. Pinned by `test/cli/generate.test.js`.
- `brails routes [filter]` lists the routes `config/routes.js` defines, in match order: verb, path, controller#action and name. It loads the routes into a `Router` without booting the app. Pinned by `test/cli/routes.test.js`.
- `brails db:create`, `db:drop`, `db:setup` and `db:reset`, so every `db:*` command works. create and drop run on the server's `postgres` maintenance database; an existing database is reported, not an error; drop and reset refuse in production without `--force`. setup is create + schema:load + seed; reset is drop + setup. Pinned by `test/cli/db_create_drop.test.js`.
- `brails db:schema:dump`, `db:schema:load` and `db:seed`. A schema load now marks every migration file up to the schema's version as run (it marked only the latest, so a later `db:migrate` re-ran the rest). `db:seed` runs `db/seeds.js` with the app's connection set for models. Pinned by `test/cli/db_commands.test.js`.
- `brails db:migrate` and `brails db:rollback [--step=N]` (also `brails db migrate`). They connect to the database `config/database.js` names, run `db/migrations`, and rewrite `db/schema.js` afterwards. App boot and the CLI pick the database through one function, `selectDatabaseConfig` (`src/database/config.js`). The other `db:*` commands still exit 1 as not implemented. Pinned by `test/cli/db_commands.test.js`.
- The app connects to the database at boot. When `config/database.js` names a database (`url` or `database`, or the current environment's block), `Application` connects, makes that the connection models use, and closes it on stop; a database it cannot reach fails boot. `brails new` writes a `config/database.js` that reads `DATABASE_URL`, and without it the app runs with no database. The demo app's config drops its localhost fallbacks, so it connects only when `DATABASE_URL` is set. Pinned by `test/core/database_boot.test.js`.
- Routing & Controllers guide (`docs/eng/routing/overview.md`). Every example in it is a complete file, which `test/docs/routing_guide.test.js` writes over a fresh `brails new` app, boots and checks. It also documents what is not implemented yet: nested resources, `scope`, filter options, and CSRF token issuance.

### Changed

- Replaced the native `bcrypt` ^5.1.1 dependency with `bcryptjs` ^3.0.3 — pure JavaScript, zero runtime dependencies, API-compatible with native bcrypt (`hash` / `compare` and their `*Sync` variants, same `$2a$` / `$2b$` hashes, so no stored digest changes shape). Native bcrypt pulled `@mapbox/node-pre-gyp@1.0.11`, which pinned `tar ^6` (`tar@6.2.1`); no tar 6.x release is patched — the advisories are fixed only in tar 7.5.19 — so the lock loses the whole subtree, not a refreshed pin. Nothing in `src/`, `demo/` or `test/` imported bcrypt. Pinned by `test/dependencies.test.js`.
- CSRF protection is off by default in the test environment, as in Rails (`allow_forgery_protection = false`), so a request test can post without fetching a session token; `security.csrf: true` turns it on for a test of the check. Every other environment keeps it on by default. Pinned by `test/core/csrf_default.test.js`.
- `Model.register()` gives each declared association a method: `await post.comments()`, `await post.user()`. They existed only after an internal `defineAssociations(Post)` nothing called, and the guide said association methods were not wired up. `includes()` now fills those methods instead of setting a property of the same name, which shadowed the method: after `Post.includes('comments')`, `await post.comments()` answers without a query, where it was `post.comments` before. Pinned by `test/database/association_methods.test.js`.
- Scopes chain on a query builder: `Post.published().recent()` and `Post.where({ author_id: 3 }).published()`; it threw "recent is not a function". A scope named like a method of the model or its query builder (`where`, `all`, `order`) throws on the model's first query, naming it; it was skipped without a word and could never be called. Pinned by `test/database/scope_chaining.test.js`.
- `save()`, `update()` and `destroy()` throw what they do not handle: a database error (a `DatabaseError` with its SQLSTATE in `code`) or an error a callback throws, including a callback that names a missing method. They caught every exception and returned `false` with the message in `record.errors.base`, so a unique violation lost its code, a bug in a callback read like a validation failure, and inside `connection.transaction()` the caller carried on and the transaction committed the rows before the failure. `false` stays for a failed validation and a `before` callback that returns `false`. Pinned by `test/database/save_errors.test.js` and, on PostgreSQL, `save_errors.pg.test.js`.
- Each attribute is also a property: `post.title` reads it and `post.title = 'x'` sets it, as `set()` does, so `save()` writes it. A plain property assignment used to be dropped by `save()` without a word. Methods, getters and fields such as `errors` keep their names; the properties stay out of JSON. Pinned by `test/database/attribute_accessors.test.js`.
- The demo app is a working JSON API for posts and their comments, tested through `request(app)` on PostgreSQL: `/health`, `/posts` (published, newest first, paginated) and `/posts/:post_id/comments`, with writes guarded by a `DEMO_API_TOKEN` filter and fields whitelisted with `StrongParams`. Its routes had pointed at controllers that did not exist (home, registrations, users, api/v1, admin), its controllers used `this.currentUser` and camelCase columns, and its sessions controller, job, mailer, channel and React components used planned APIs that throw; those are gone.
- CI runs the demo app's test suite against PostgreSQL (its steps had been commented out: "Demo tests require database implementations"). The demo's models, factories and test now use the framework's API: `get` / `set`, snake_case columns, `beforeValidation`, `Model.register()`, `loadAssociation`; the `User` model drops the `password` attribute and `hasSecurePassword`, which wait on authentication.
- A request body that does not parse (truncated JSON, say) answers `400` with `Malformed request body: ...` instead of running the action without it. An empty JSON body still means no params.
- Dispatch matches requests with `Router#match`, the one matcher, instead of its own: a trailing slash matches (`/posts/7/` is `/posts/7`), and a `*` segment matches one segment as `params.splat`. `Router#match` compares static segments case-sensitively, as dispatch did (its own check was dead, so `/Posts` matched `/posts`).
- `router.middleware(list, callback)` throws `NotImplementedError`: it ran the callback without adding the middleware, so routes meant to be guarded by it were not. `Channel#stream` throws too: it recorded the stream and subscribed to nothing. `test/support/no_silent_stubs.test.js` now fails on any function under `src/` that holds a TODO and never throws, which catches a body that computes and returns (as `assertJson` did), not only an empty one.
- `includes()` with an association the model does not declare throws, naming the declared ones, instead of skipping it with a warning, which left the property undefined.
- `connection.transaction(callback)` throws the callback's own error after the rollback, instead of wrapping it in `DatabaseError("Transaction failed: ...")`, which dropped its type: a `RecordNotFoundError` or a failing test assertion came back as a `DatabaseError`. A statement that fails inside the callback is a `DatabaseError` naming the query and its SQLSTATE, as outside a transaction. Pinned by `test/database/transaction_errors.test.js`.
- A planned API throws `NotImplementedError` (exported from `bun-on-rails`) instead of resolving `undefined`. 96 functions did nothing while looking like they worked: `Job.performLater` / `performIn` / `performAt` queued nothing, `Mail#deliver` sent nothing, `Storage#upload` stored nothing, the Redis cache store was a permanent miss, `withinTransaction(cb)` never ran `cb` (so a test inside it passed without running), `request.get()` resolved `undefined`, and the React hooks and forms returned placeholders. Each now names itself and its planned feature: `Job.performLater is not implemented yet (planned: queued jobs; see "Planned" in the README)`. `test/support/no_silent_stubs.test.js` parses `src/` and fails on a function whose body is only TODO comments, or TODO comments and a `return`.
- The npm package is `bun-on-rails`. The old name, `@bun-on-rails`, was a scope with no package name: a clean `bun add -g` of the tarball failed with `invalid dependency name "@bun-on-rails"`. `files` now limits the tarball to `src/` plus the `package.json`, `README.md` and `LICENSE` that npm always adds: 47 files instead of 159 that included `test/`, `demo/`, `docs/` and the agent config. `homepage` points at the GitHub Pages docs site instead of the unresolvable bunonrails.com. `test/package_manifest.test.js` pins all three.
- Unimplemented `brails` commands (`generate`, `db:*`, `console`, `routes`, `test`, `credentials`) no longer print the results of work they never did, such as "Migrations complete.", made-up routes or "Tests complete.". They exit 1 with `brails <cmd> is not implemented yet`, and `brails help` lists them under Planned. `test/cli/not_implemented.test.js` pins this, and it requires any new command to be implemented or declared unimplemented.
- `brails new <app-name>` creates the app. It used to print "Application created successfully!", exit 0, and create nothing. It now writes routes, a home and a health controller, `package.json` (depending on this package at its own version), `.gitignore` and `.env.example`, then runs `bun install` (`--skip-install` skips it). The app answers `GET /` and `GET /health` with no database. It refuses invalid names and existing directories. Pinned by `test/cli/new.test.js`.
- The getting-started docs (introduction, installation, quick start, project structure) describe what works today. Gone: `bun create`, `bor --version`, `bun setup`, the scaffold-generator tutorial, the SQLite/MySQL claims and bunonrails.com. The quick start builds a posts resource, and `test/docs/quick_start.test.js` runs its code over a fresh `brails new` app. The introduction separates "What works today" from "Planned".
- The README matches the code. The Quick Start starts with `bun add -g bun-on-rails` and contains only working steps (no `brails setup`). The example is a routes file and a controller that run. Features are split into "What works today" and "Planned". The docs link points at `docs/`. `test/docs/readme.test.js` pins the install line, checks that every `brails` step shown is implemented, and runs the example.
- The release workflow is safe to run for the first time. It refuses a tag that differs from `package.json`'s version and runs `bin/qa-release` before publishing. It publishes through npm trusted publishing (Node 22, npm 11.5 or later, `--provenance`, no long-lived `NPM_TOKEN`). The first release's changelog starts from the root commit, and the release body's install line comes from `package.json`. `test/release_workflow.test.js` pins each of these.
- The remaining docs pages describe what works today. The database pages (overview, models, queries, migrations) document the ORM as `src/database/` implements it, every example checked against PostgreSQL: the app does not connect at boot, so you connect in an initializer; migrations run from a script with `MigrationRunner`; PostgreSQL is the only adapter. The jobs, deployment, core-concepts and vibe-coding pages and the site home page drop commands and features that do not exist (`bun dev`, `bun generate`, `brails setup`, generators, `db:*` commands, SQLite, auth) and list them under "Not implemented yet". Imports use `bun-on-rails`, not `@bun-on-rails` or subpaths. The authentication page is removed: no auth module ships. `docs/README.md` no longer links to the missing `idea/` and `standards/` folders.
- The docs site config is fixed. It sets `base: '/bun-on-rails/'` (the GitHub Pages project path, so the site loads with its styles), `ignoreDeadLinks: false` (a dead internal link now fails `bin/check` and CI), and `srcExclude` for `plans/**` and `README.md`. The sidebar lists every page, and the nav no longer links the missing `core-concepts/overview`. `test/docs/site_config.test.js` pins these settings and keeps the sidebar and pages in step.

### Fixed

- A model method named like a lifecycle hook but not quite (`beforeValidate`, `afterSaved`) throws on the first validation, save or destroy, naming the hook it was meant to be. The framework never called it, so its work silently did not happen.
- Request params are parsed once, with nested keys. Dispatch flattened the query string (`filter[status]=draft` gave `params["filter[status]"]`) and form bodies, and read the body itself, so the body parser middleware read a consumed request and logged "Failed to parse request body" on every `POST`. The query string now nests through `parseQueryString`, and the body is read once, by `bodyParser`, through `parseBody`. Pinned by `test/core/dispatch_params.test.js`.
- Route params are URL-decoded on the request path: `/tags/hello%20world` gave `params.name` `"hello%20world"`. Pinned by `test/core/dispatch_matching.test.js`.
- A file under `app/` that fails to import fails boot, naming the file and the error. Boot logged "Failed to load" and went on, so an app with a syntax error in a controller started and answered 404 for its routes. Pinned by `test/core/boot_loading.test.js`.
- `factory.build` / `factory.create` built the base `Model` for every factory (saving to a table named `models`), never the model the factory is for. A factory now builds the class given as `model` (a class or a registered name, `factory.define('admin', attributes, { model: 'User' })`), else the registered model named after it, and throws naming both fixes when there is none. Pinned by `test/testing/factory.test.js`.
- Generated SQL no longer ends in `LIMIT null OFFSET null` when a query has no limit or offset: the query builder uses `null` for none, and the adapter only skipped `undefined`.
- `TestResponse#assertJson` and `#assertJsonHas` passed whatever the body held: each read the JSON and returned. `assertJson` now deep-compares and `assertJsonHas` follows a dotted key path, each throwing with what it found.
- Boot refuses a config that names a backend the framework does not have, before anything connects. `cache.store: 'redis'` ran the memory store behind a warning, `jobs.adapter: 'bullmq'` logged "Job queue initialized with BullMQ" and queued nothing, `jobs.worker: true` logged "Job workers started", and `websocket.enabled: true` logged "WebSocket enabled" with no upgrade path. Each now throws `NotImplementedError`, and an unknown `cache.store` or `jobs.adapter` throws naming the built-in one. The demo's production config, which named Redis for the cache and the session and so could not boot, uses the memory stores. Pinned by `test/core/boot_backends.test.js`.
- Controller filters work on the request path. Dispatch ran its own loop over `beforeAction` / `afterAction`: a plain list of names, no `only` / `except`, and the object form `{ authenticate: { except: [...] } }` (as the demo app writes it) threw, so those requests answered 500. Dispatch now uses `ControllerMiddleware`'s runner, which takes every form with `only`, `except`, `if` and `unless`. A filter naming a method that does not exist fails the request instead of being skipped with a warning, which silently disabled a misspelled auth filter. Pinned by `test/controller/filters_dispatch.test.js`.
- `DatabaseError#code` is the PostgreSQL SQLSTATE again (for example `23505`). Bun.SQL reports it as `errno` and puts a generic `ERR_POSTGRES_SERVER_ERROR` in `code`, so since the native driver became the default (F12) the code no longer identified the error. Pinned in `test/cli/db_create_drop.test.js`.
- `MigrationRunner#migrate()` creates `schema_migrations` once per run. It ran `CREATE TABLE IF NOT EXISTS` twice, and PostgreSQL answered the second with a NOTICE that postgres.js prints. Pinned by `test/database/migrations_table.test.js`.
- The native `Bun.SQL` driver is used. `connect()` called `Bun.sql({...})`, but in Bun 1.2+ `Bun.sql` is the default client (a tagged-template function), so that built a query helper, the connection test threw "SQLHelper is not a function", and every connection fell back to postgres.js with a warning. It also passed `connectionTimeout` in milliseconds where Bun takes seconds. The client is now `new Bun.SQL(...)`. Pinned by `test/database/bun_sql.test.js`; on PostgreSQL 16 the native path gives the same results (string ids, counts, rollback, associations).
- `first()` and `last()` work after a join, and columns can be qualified with their table. Both ordered by the bare primary key, which a join makes ambiguous, and every column reference was quoted as a single identifier, so `"users.name"` named a column literally called `users.name`. Column references in SELECT, WHERE, GROUP BY and ORDER BY now split `table.column` (and keep `posts.*`), and `first()`/`last()` order by the qualified primary key. Pinned by `test/database/qualified_columns.test.js` and verified against PostgreSQL 16.
- A schema dump loads. `dumpSchema` wrote tables in alphabetical order with their foreign keys inline, so `loadSchema` created `comments` before the `posts` it references and failed. Tables are now ordered so every referenced table comes first (alphabetical among independent ones). A foreign-key cycle throws at dump time, naming the tables. Pinned by `test/database/schema_order.test.js`, and verified against PostgreSQL 16 by dumping users, posts and comments and loading them into an empty database.
- `new MigrationRunner(db, "db/migrations")` works. The runner imported each file by a path built from the directory as given, so a relative directory resolved against `src/database/` (or as a package name) and failed to import. It is now resolved against the working directory. Pinned by `test/database/migration_paths.test.js`.
- Model queries inside `connection.transaction()` join the transaction. Models always used the global connection, so a rollback did not undo them and `lock()` held its row lock only for its own statement. Inside the callback, `getConnection()` now returns the transaction's connection (scoped with `AsyncLocalStorage`, so concurrent queries outside it are unaffected), and a nested `transaction()` joins the open one. Pinned by `test/database/transactions.test.js`. Verified against PostgreSQL 16: a rollback undoes a model insert, and a second `FOR UPDATE` waits for the first transaction to commit.
- Association classes resolve. `loadAssociation` used a string `model` as the class, so it crashed, and it looked a `hasMany` like `comments` up as `Comments`, so it never resolved. The eager loader and `includes()` singularized by stripping a trailing "es", so `notes` became `Not` and `images` became `Imag`. One resolver, `resolveAssociationModel`, built on the inflector's `classify`, now serves all three. Pinned by `test/database/association_models.test.js` and verified against PostgreSQL 16.
- `save()` refreshes `updated_at` on every update. It set the column only when it was missing, and a loaded record always has it, so updates kept the old value. A model whose table has no timestamp columns can now save, with `static timestamps = false`; before, every insert and update wrote both columns and failed. Pinned by `test/database/timestamps.test.js` and verified against PostgreSQL 16.
- `updateAll`, `deleteAll`, `Model.updateWhere`, `Model.deleteWhere` and `Model.deleteAll` return the number of rows they changed. They returned `result.length`, the rows the statement returned, which is 0 without `RETURNING`. Both drivers report the affected rows as `count`; a result without one now throws instead of reporting 0. Pinned by `test/database/write_counts.test.js` and verified against PostgreSQL 16.
- String conditions take bound values: `where("views > ? AND views < ?", 10, 100)`. The `?` was sent unchanged and the parameter index never advanced, so the SQL was invalid and any later condition was misnumbered. `Model.where` also dropped the values. Each `?` (or `$n`) is now bound at the right index, a `?` inside a quoted literal is left alone, and a count mismatch throws. The query builder's duplicate WHERE builder, used by `updateAll` and `deleteAll`, now delegates to the adapter's. Pinned by `test/database/raw_conditions.test.js`.
- One table-name rule. `save()` named a model's table with `tableize()` (`Category` becomes `categories`), but the query builder appended `s` to the snake-cased class name (`categorys`, `persons`, `addresss`), so a saved record could not be found, updated or deleted. `t.references()` and the schema dumper also appended `s`. The query builder, `references()` and the dumper now use the inflector, like `save()`. Pinned by `test/database/table_names.test.js`.
- A `postgresql://` database URL works. `parseDatabaseUrl` stripped "sql" from the scheme, which turned `postgresql` into the unsupported adapter `postgre`, so only `postgres://` URLs could connect. Verified against PostgreSQL 16 with both schemes.
- An initializer that throws now fails boot. `_runInitializers` rethrew the error, but its own outer `catch`, meant for a missing directory, swallowed it as "No initializers directory found", so an app whose database initializer failed booted anyway and answered 500 to every query. `brails dev` now exits 1 with `Initializer config/initializers/<file> failed: <cause>`. Pinned by `test/core/initializers.test.js`.
- Writes work with CSRF protection on. The csrf middleware checked `X-CSRF-Token` against `session.csrfToken`, but nothing set that token, so every POST/PUT/PATCH/DELETE got `403 CSRF token mismatch` unless the app turned CSRF off. The session middleware now gives each session a random token, and actions read it as `this.csrfToken`. `test/controller/csrf_token.test.js` covers the round trip, and the Routing & Controllers guide shows it (`GET /csrf`).
- Docs deployment: the `Deploy Documentation` workflow made its `build` job depend on a GitHub Pages site that only a repository admin can create. Run 42344720510 (push of `bc4d6c8c`, the merge of PR #23) annotated that job with `Get Pages site failed. Error: Not Found` — the workflow token could read the Pages API, the site simply does not exist — and `Create Pages site failed. Error: Resource not accessible by integration`: creating a Pages site is a repository-administration operation that no workflow `permissions:` block can grant `GITHUB_TOKEN`. PR #23 could not have fixed it: it pinned `actions/configure-pages` to `v6.0.0` with `enablement: true`, which turns the action's read-only lookup into exactly that Create call, while its `Preflight Pages site` step was `continue-on-error: true` and only printed a warning — so the run stayed red. `docs.yml` now probes the Pages API read-only before `Build documentation`, records readiness as the `pagesReady` job output, always uploads `docs/.vitepress/dist` with `actions/upload-artifact`, and gates both `actions/upload-pages-artifact` and the `deploy` job on that output: a missing site leaves the build green with a `::warning` annotation naming the required setting and the deploy skipped. `actions/configure-pages` and `enablement:` are gone. The remaining step is human: **Settings > Pages > Build and deployment > Source = "GitHub Actions"**.
